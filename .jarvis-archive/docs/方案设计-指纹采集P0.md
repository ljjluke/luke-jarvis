## 模块骨架（P01–P05）

调用链：
```
RpcImpl 入库点 → FpOrchestrator.onRecordSaved(assetId, port)
  → A 通道：FpParseService(解析) → FpMatcher(规则归一) → FpInfer(implies 推断) → FpResolver(去重消解) → 落库
  → 若 required 缺口且强度允许 → C 通道（P0 不启用）
全部入口包 if (SystemConfig.fpEnabled)，异常一律 catch 不冒泡
```

- **FpParseService**：`parseText(assetId, port, raw, evType)`，只产出结构体不写库（便于单测）。`Version:`→exact；CPE 行拆 vendor/product/version；`X-Powered-By: PHP/7.4.3`→PHP+7.4.3(confidence=high)；无版本→family 且 product_version=NULL；无论命中与否都写 `fp_evidence.raw`
- **FpMatcher**：预编译正则静态 Map；先跑 negatives（命中即跳过整条规则）；版本提取 `version_tpl` group(1)，抽不到且 versionRequired 则整条不命中，否则 family；confidence：直证版本=high / 强特征无版本=medium / 单弱特征=low
- **FpInfer**：BFS 从 seeds 按 implies 展开；推断产物 product_version 一律 NULL、confidence=min(父,implies)；防环（category+product visited）；深度上限 3；单资产产物上限 50；与直证冲突保留直证、推断降 low
- **FpResolver**：唯一键 (asset_id, port, category, product) upsert；granularity 高者胜 → confidence 高者胜 → 不决则两条并存并标 conflict=1；命中刷新 last_seen，不删除历史；**写库前硬断言 family 且 product_version!=null ⇒ 拒绝写入并记日志**

## 总体方案

被动优先、零新增请求。三通道设计，P0 只启用 A 通道：
- **A 通道（被动解析，P0 唯一启用）**：从既有文本解析 → 规则归一 → implies 推断 → 去重消解 → 落库。零网络请求。
- **B 通道（证据回捞）**：P0 不启用。
- **C 通道（主动探测）**：P0 不启用（FpProber 只留骨架，不进主链路）。

数据流：
```
RpcImpl 三个 save 点
  → FpOrchestrator.onRecordSaved(assetId, port)   [if(fp.enabled) + try/catch]
    → FpParseService.parseText()  → List<ParsedItem>（不写库）
    → FpMatcher.match()           → List<MatchResult>
    → FpInfer.infer()             → 追加 implies 产物（version=NULL）
    → FpResolver.resolve()        → upsert + 硬断言
    → 落 fp_finding / fp_evidence / fp_scan_stat
```

## 模块划分

| 模块 | 对外方法 | 输入 | 输出 | 谁调它 |
|---|---|---|---|---|
| FpOrchestrator | `onRecordSaved(String assetId, Integer port)` | assetId, port | void（副作用落库） | RpcImpl 三个 save 点 |
| FpParseService | `parseText(String assetId, Integer port, String raw, EvType type)` | 原始文本 + 证据类型 | `List<ParsedItem>`（不写库） | FpOrchestrator |
| FpMatcher | `match(List<ParsedItem>, FpContext)` | 解析产物 + 上下文 | `List<MatchResult>` | FpOrchestrator |
| FpInfer | `infer(List<FpFinding> seeds)` | 直证结果 | `List<FpFinding>`（version 恒 null） | FpOrchestrator |
| FpResolver | `resolve(String assetId, Integer port, List<FpFinding>)` | 待落库结果 | 实际落库条数 | FpOrchestrator |
| FpRepository | `upsertFinding / insertEvidence / upsertStat / listByAssetPort` | — | — | Resolver / Controller |
| SystemConfig | `fpEnabled() / fpStrength()` | — | boolean / String | Orchestrator |

**契约约束**：FpParseService 不写库（便于单测）；FpResolver 是唯一写 fp_finding/fp_evidence 的出口；Controller 只读。

## 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| RpcImpl 行号与文档不一致 | 接线点插错位置 | 实现前先 `grep -n` 复核三处 save 完成点，按语义定位不按行号 |
| RedImpl 入库点在事务内，新增解析拖慢主流程 | 扫描结果入库变慢 | 解析纯内存、无 IO；FpOrchestrator 异常全 catch；必要时评估异步化（P0 先同步，实测耗时>100ms 再评估） |
| family+version 断言被绕过 | V1 不为 0 | 断言写在 FpResolver 写库前唯一出口，不依赖事后对账 |
| 规则误报（通用错误页被判为框架） | 假指纹 | negatives 先跑；出厂 enabled=0；正负例实测后才开 |
| JSP 改动影响现有端口表 | 页面回归 | 新增区块插入在端口表下方，不改既有 DOM 与字段 |
| Eclipse 工程无 pom，编译方式不统一 | 出包失败 | 按 H07 先确认 javac 方式与依赖 jar 来源，写进回报 |
| 存量无 ports 资产 | 回填率低 | 只回填 ports 非空资产，不承诺全量 |
