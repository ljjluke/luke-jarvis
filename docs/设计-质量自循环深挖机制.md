# 质量自循环深挖机制 · 设计文档

> 版本 v0.1（设计稿，待评审后落地）
> 背景：scan 用户对产物质量反复不满（认证弹窗纠正 3 次/任务表格不好看/细节差异 21 处）——现有机制管"完整性"（没漏：参照基准/走查/coverage 销项），**不管"质量"（做得好不好）**。本设计补"质量自循环深挖"：**不同领域深挖细节的自循环机制**。

## 一、核心概念

### 1.1 完整性 vs 质量（先分清）
| | 完整性（已有） | 质量（本设计补） |
|---|---|---|
| 管什么 | **没漏**：原物有的新成果都有 | **做得好**：设计优不优/体验顺不顺/健壮不健壮/专业不专业 |
| 参照 | 参照基准（旧版/原物，具体物） | **质量维度清单**（本领域"细节要深挖哪些"） |
| 现有机制 | 参照基准/走查/coverage 销项/taskgraph 逐项对照 | **缺**（质量评审×0/质量基准×0） |

### 1.2 为什么"自循环"（不是一次评审）
- 质量是**逐步逼近**的：第一次评审必然挑出毛病 → 修复 → 再评又发现更深的问题 → 再修……
- **一次评审就收口 = 只发现表层问题**（scan 教训：评审/验收过但仍被用户挑出 21 处）
- **自循环终止判定 = 连续一轮清单全部维度无毛病**（不是"评过一轮"）

### 1.3 为什么"不同领域"（细节维度不预设）
- 领域无关铁律：**插件不预设任何领域清单**（软件=子页/字段/交互；制造=工序/质检/公差；开店=陈列/服务/库存——完全不同）
- **细节维度清单 = CEO 按本单领域现场生成**（软件=界面/交互/边界/性能/健壮性；制造=工序完整性/质检点/公差/交付文档；开店=动线/陈列/服务/库存/收银……）
- 工具只给"通用骨架 + 现场生成要求"，**不给领域模板**（防 CEO 偷懒照抄）

## 二、机制设计（三件套）

### 2.1 ① 质量维度清单（现场生成，领域无关）
**产物**：`<项目>/.jarvis/docs/质量细节维度-<需求关键词>.md`

**生成时机**：方案设计定稿后、写实现前（CEO + 领域专家按本单领域定）

**清单内容**（每条维度 = 一个"细节要深挖的方向" + "达标判据"）：
```
维度1: <本领域细节方向> —— 达标判据: <怎么算这一维度做得好>
维度2: ...
```
**领域无关骨架**（通用提示，不是领域模板）：
- 结构维度：产物的构成部分是否完整、组织是否合理
- 行为维度：功能/交互是否符合预期、边界情况（空/错/快/慢/大/小）
- 体验维度：使用者视角是否顺/清晰/不别扭
- 健壮维度：异常/故障/极端输入是否扛得住
- 专业维度：是否符合该领域的专业水准/规范
- **领域特有维度**：CEO 按本单领域补（软件=响应式/兼容/性能；制造=公差/质检点；开店=动线/陈列）

**铁律**：
- **不许抄别的项目的清单**（不同领域/规模/约束，清单不同）
- **不许用通用词糊弄**（"做好""优化"不算判据——每条判据须可判定）

### 2.2 ② 质量评审（独立角色 + 对照清单挑毛病）
**评审角色**：**非实现者**（独立于实现角色的角色——实现者自己评自己 = 自己说自己好，同"测试独立于开发"）

**评审动作**：对照《质量细节维度清单》逐维度检查产物，产出**质量评审单**：
```
评审单 · 第N轮
维度1: ✅ 达标 / ❌ 问题：<具体毛病+在哪+为什么不行>
维度2: ...
剩余问题: X 条
```
**评审证据**：每条问题写"在哪/什么现象/为什么不符合判据"（不是"我觉得不好"）

### 2.3 ③ 打磨循环（自循环，达标才收口）
```
产物完成 → 质量评审(第1轮) → 有剩余问题？
  有 → 实现者修复 → 质量评审(第2轮) → 有剩余问题？
    有 → 修复 → 再评 ……
    无 → 达标，收口
```
**循环终止判定**：
- **连续一轮评审"清单全部维度无毛病"** → 达标
- **不许"评过一轮就收口"**（自循环强制）
- **循环轮次留痕**：每轮评审单存 `<项目>/.jarvis/reports/质量评审-<需求>-第N轮.md`（可追溯：第几轮、挑出什么、修了什么、剩余什么）

**⚠️ 收敛条件（防无限循环——评审永远挑得出毛病→永远不交付）**：
- 正常收敛：连续一轮全 ✅ → 达标收口；
- **连续 ≥3 轮剩余问题未减少（每轮都剩同样的/类似的毛病）→ 停止自循环、上报 CEO 判定**：①判据过严（标准高于用户预期）→ CEO 与用户确认后放宽判据；②问题真实存在但实现能力不足 → 走"换人/补强"；③问题无法在本单解决 → 降级并标注（同"可降级"机制）——**自循环不是无限循环，收敛不了一定要有人拍板**。

## 三、与现有机制的关系（不重复造轮子）

| 现有机制 | 关系 |
|---|---|
| 参照基准/完整性对照闸 | 管"没漏"（完整性）；质量维度清单管"做得好"（质量）——**两个都要** |
| taskgraph 替代类验收 | 验收写"逐项对照+真实验证"（完整性侧）；质量评审在实现后补"做得好" |
| coverage 差异销项 | 差异清单销项（完整性侧）；**质量评审单可同样用 coverage 模式核销**（源=质量维度清单、目标=评审修复证据） |
| 开发-测试迭代循环 | 功能正确性循环；质量打磨循环是它的"质量侧"补充（不是替代） |
| 用户视角走查闸 | 走查=以用户身份用一遍（体验侧）；质量评审=对照清单逐维度评（更系统） |

## 四、代码化落点（自循环怎么强制）

**核心：循环不许停在中间、不许"评一轮就收口"**——工具强制：

### 方案 A（推荐）：`jarvis_quality` 新工具
- 维护**质量循环状态**：`{ 清单维度, 当前轮次, 剩余问题, 达标判定 }`
- 动作：
  - `define`（CEO 现场生成质量维度清单，领域无关校验：非空/判据可判定/不许抄模板）
  - `review`（提交第 N 轮评审单：每维度 ✅/❌ + 问题 + 证据）
  - `status`（查循环状态：第几轮/剩余问题/是否达标）
- **硬闸**：`review` 提交后若剩余问题 > 0 → 状态 = 未达标，**不许收口**（后续收口查 status）；连续一轮全 ✅ → 达标
- **衔接收口**：收口防迎合总闸/交付检查加"质量循环达标"项（status=达标 + 评审单留痕）

### 方案 B（轻量）：复用 jarvis_coverage
- 源 = 质量维度清单条目、目标 = 每轮评审修复落点（evidence=评审证据）
- coverage 天然查"未覆盖/无证据/未收口"——但**不维护"轮次状态"**（不知道是第几轮、循环有没有真正收敛）

**设计选择**：方案 A（jarvis_quality）更贴合"自循环"（有轮次/收敛状态），方案 B 可作补充（质量清单销项）。**推荐 A 为主 + B 兜底**。

## 六、诚实边界（不假装能 100% 保证质量）

- **质量评审提高的是"下限"**（从"没人管好不好"→"有基准+独立评审+循环到达标"）——这是质变
- **但"好不好"的最终标准 = 用户认可的质量基准**（需求阶段确认）——评审是"对照用户认可的参照挑毛病"，不是工具凭空判质量
- **评审深度受评审角色能力影响**（角色卡质量好=评得深）——已有 distill 深度闸兜底
- **"自循环"防的是"评一轮就收口"**（工具强制），防不了"评审本身评得浅"（靠质量维度清单的判据可判定 + 独立角色兜底）
