# 插件执行流程（长什么样、每步谁干什么、事实落在哪）

> 一句话：**插件不是提示词，是一台"阶段机 + 工具集 + 状态目录"**。
> 用户的活从"一句话"进来，被切成六段，每段有产物文件、有下一步工具、有禁止动作；
> 阶段由**磁盘事实**计算（不是模型自述），所以换会话、上下文压缩、换模型都不影响进度。

---

## 一、角色与边界

```
用户
 │  一句话需求
 ▼
贾维斯 / captain（顶层）          ← 只做：接单 / 派活 / 盯控 / 裁决 / 回显
 │                                 绝不写文件、跑命令、亲自实现
 │  jarvis_* 工具（31 个）
 ▼
agent-teams 团队                  ← 成员各有角色卡（.jarvis/cards/）
 │                                 按卡的方法论思考，产物回传（路径/实测/来源）
 ▼
交付物 + .jarvis/ 状态（记忆）
```

插件在两个切面介入：

| 切面 | 介入内容 | 代码位置 |
|---|---|---|
| **每次请求**（systemPrompt） | ① `luke-jarvis:protocol`（order 118）协议正文、企业文化、铁律；② `luke-jarvis:stage`（order 119，按 agent 注册）**当前第几步/缺什么/下一步/事实快照** | `src/host/plugin.js`、`gates/stage.js#renderStage` |
| **每次工具调用**（guard 链） | 三个 guard 顺序执行，任一返回字符串 = 拒绝该次调用：① `captainExecutionGuard` 顶层不许亲自干 ② `jarvisStageGate` 越阶段工具拒绝 ③ `jarvisFlowGuard` 流程产物闸 + 记忆保鲜 | `plugin.js` 496-498 行 |

## 二、六阶段状态机（阶段由文件事实算，不看模型自述）

| # | 阶段 | 产物（磁盘事实） | 过闸条件 | 本阶段禁止 |
|---|---|---|---|---|
| 1 | clarify 需求打磨 | `.jarvis/docs/需求规格-*.md`（≥300 字 + 每条带可判定「验收」） | 文件存在 + 实质校验 + `jarvis_flowguard(step="clarify")` | 建队/加人/派活/拆解/收口/改版本账本 |
| 2 | decompose 拆解 | `.jarvis/docs/任务编排-*.md`（`jarvis_taskgraph` 产出+结构校验） | 文件存在 + `flowguard(step="decompose")` | 建队/派活/收口 |
| 3 | design 方案设计 | `.jarvis/docs/方案设计-*.md`（每条需求→实现落点） | 文件存在 + `flowguard(step="design")` | 建队/派活/重拆/收口 |
| 4 | build 建队派活 | `.jarvis/cards/` ≥2 张卡 + `.agent-teams/<team>/team.json` | 人才层前置（猎头卡/带队卡/岗位卡）+ `flowguard(step="build")` | 认领/改验收契约/重拆/收口 |
| 5 | execute 执行盯控 | 团队任务全部 completed | `flowguard(step="execute")`：无 captain 自领任务、无卡死任务 | 改基线/重拆/改版本账本 |
| 6 | close 收口 | 黑板归拢 + 覆盖矩阵（改造类）+ 三产物闭环 | `flowguard(step="close")`：黑板无假未决、覆盖矩阵逐条有落点、需求→方案→测试闭环 | 新派活/加人 |

`computeStage()` 每一步都返回 `missing[]`（缺什么）和 `next`（下一步做什么）——这是模型唯一的纠错输入，也是你在 UI/日志里看到的"现在卡在哪"。

## 三、一次真实任务的完整时序

```
用户：做个会员复购增长方案
 │
 1. jarvis_project(requirement)            → S/M/L 分级，决定要不要建队
 2. jarvis_store(check)                    → 读 .jarvis/project.md 续接（有记忆就直接接着干）
 3. jarvis_clarify(analyze/ask/confirm)    → 只问真疑问；restate 需求本质（为谁/解决什么/怎样算成功）
 4. 写 .jarvis/docs/需求规格-*.md           → 每条功能带可判定验收
 5. jarvis_flowguard(step="clarify")       → 写 .jarvis/gates.json.clarify = {ok:true}
    ├── 不足 300 字/无「验收」→ BLOCKED，给明确补什么
    │
 6. jarvis_taskgraph(tasks)                → 校验依赖闭环/无循环/每任务可判定验收
 7. 写 .jarvis/docs/任务编排-*.md → flowguard(step="decompose")
    │
 8. 写 .jarvis/docs/方案设计-*.md → flowguard(step="design")
    │
 9. jarvis_distill_guide(role, material)   → 先提炼"这个人的 HOW"（决策触发词/独特取舍/失效边界）
10. jarvis_distill(role, card)             → 六段式 + 证据链 + 真实 source 校验，不合格不收
11. jarvis_store(save, card)               → .jarvis/cards/<角色>-<人物>.md
    └── 至少 2 张（带队卡 + 岗位卡）；人才层还要猎头卡
    │
12. jarvis_perf / jarvis_collab            → 定角色协同段、绩效口径（角色不是各干各的）
13. flowguard(step="build")                → 产物 + 人才层齐备才过
14. agent_teams_create + agent_teams_add_member（先 status 查重）
    │
15. jarvis_dispatch_task(assignee, subject, description, acceptance)
    ├── 内部 jarvis_member_brief：角色卡全文 + ponder 指引 + 回报格式
    └── 内部 agent_teams_create_task：须知自动拼进描述 → 任务真的建出来
16. agent_teams_reassign_task              → 唤醒成员会话
    │
17. 成员按角色卡工作 → jarvis_board 登记问题/发现/决策/风险（共享黑板）
    └── 卡住：jarvis_escalate（问题/已尝试/风险/要什么决策，缺项打回）
    │
18. 成员 agent_teams_update_task(completed) → 交回交付物路径 + 实测 + 来源
19. jarvis_perf(role, stageStatus, ...)     → 阶段考核：对齐度 0 直接换人
    └── 不达标：remove_member + add_member（end-seed 成员不可 reassign）
    │
20. jarvis_coverage(source, targets, persist=true) → .jarvis/docs/覆盖矩阵-*.json（逐条有落点）
21. jarvis_essence(requirement, decision)   → 防迎合/防幻觉四查，不过禁止定稿
22. flowguard(step="close")                 → 黑板归拢 + 覆盖矩阵 + 三产物闭环
23. jarvis_snapshot                          → 本次工作快照（.jarvis/sessions/），换会话可续
```

## 四、三条子流（每个阶段实际在跑的"业务"）

### 1) 需求流（clarify）

```
jarvis_clarify(analyze) → 5 角度候选问题（P1 场景/P2 现状/P3 痛点/P4 期望/P5 验收）
jarvis_clarify(trigger) → 机械判定要不要现场蒸馏该领域大佬（T1-T5）
jarvis_clarify(ask)     → 三阶提问（开放→聚焦→确认），真疑问问尽，不设数量上限
jarvis_clarify(confirm) → 需求本质三段式重述 + 假设分级（已确认/推断待确认）
→ 用户确认 → 需求规格 → flowguard(clarify)
```

### 2) 人才流（decompose → build）

```
拆解出岗位 → 每个岗位蒸馏一张卡（六段式）→ 校验（jarvis_distill）
→ 落盘 .jarvis/cards/ → 建队前人才层前置：猎头卡 + 带队卡(CEO) + 岗位卡
→ jarvis_collab 定协同段（位置/依赖/介入时机/协同方式，防各干各的）
→ 建队 → 派活（dispatch 一步到位，卡+须知自动进任务描述）
```

### 3) 交付流（execute → close）

```
成员干完 → 产物落盘（代码/文档/数据）
→ 黑板登记决策与风险（jarvis_board）
→ 覆盖矩阵（改造类：基线清单 → 每条有落点，jarvis_coverage persist）
→ 三产物闭环：需求规格 → 方案设计 → 测试/验收单，逐条对得上
→ flowguard(close) → jarvis_essence → 交付 + jarvis_snapshot
```

## 五、闸清单：留什么、为什么、不再考核什么

**保留（这些是流程本身 + 安全底线）**

| 闸 | 拦什么 | 为什么 |
|---|---|---|
| `captainExecutionGuard` | 顶层调用 write/edit/bash 等实干活工具 | 顶层亲自干 = 团队形同虚设（scan 实证） |
| `jarvisStageGate` | 越阶段工具（clarify 期就想建队/派活） | 跳步 = 缺陷；拒绝文案含"第几步/缺什么/下一步" |
| `jarvisFlowGuard` 产物闸 | 需求规格/任务编排/方案设计/人才层缺失就建队派活 | 流程产物是流程的骨架 |
| 记忆保鲜（6h） | `.jarvis/project.md` 超 6h 未更新还继续 | 长会话压缩后工作丢光 |
| close 闸 | 黑板假未决、覆盖矩阵缺落点、三产物断链 | 收口质量 |
| 状态根隔离 | 插件仓库自身当 jarvis 状态根 / 归档团队混入活跃统计 | 防假状态、防串项目 |

**不再是闸（用户定调：固化流程，不考核步骤）**

| 原来 | 现在 |
|---|---|
| 交活必须有 ponder-verify PASS 记录 | 不要求；验收看产物与证据（交付物/实测/来源） |
| 派活描述里必须有「开工须知」标记 | 不校验；`jarvis_dispatch_task` 自动拼进去 |
| assignee 有卡但描述没卡段 → 拒 | 不校验；dispatch 自动注入卡全文 |
| close 必须每个成员都有 ponder 核验 | 不要求 |

> 取舍：没有执法闸后，captain 若绕过 dispatch 直接建任务，成员可能拿不到卡——兜底是产物验收与阶段推进。
> 设计意图是：**正确的路（dispatch）已经是最省事的路**，不需要闸去查表。

## 六、状态目录（插件的"数据库"）

```
<项目>/.jarvis/
├── project.md              项目记忆（当前进度/下一步/未决项/团队清单/关键决策）——6h 保鲜
├── board.json              黑板：问题/发现/决策/风险/阻塞/接口变更（团队共享）
├── gates.json              闸门留痕：clarify/decompose/build/close = {ok:true, at}
├── lessons.md              结构化教训（分类/主责/现场/修向/状态/复现）
├── active-team.json        归属标记：哪个团队属于本会话（防别家缺口串进来）
├── company-state.json      3D 办公室数据源（员工/会议/招募/CEO/猎头位置）
├── docs/
│   ├── 需求规格-*.md        阶段 1 产物（≥300 字 + 验收）
│   ├── 任务编排-*.md        阶段 2 产物
│   ├── 方案设计-*.md        阶段 3 产物
│   ├── 覆盖矩阵-*.json/md   阶段 6 产物（改造类必做）
│   └── ponder-verify/       ponder 核验记录（可选，不再是通行证）
├── cards/                  角色卡（六段式）；history/ 放旧版
├── prototypes/             真实人物素材
├── tickets/ decisions/     任务单与裁决状态机
└── sessions/               会话快照（jarvis_snapshot）

<项目>/.agent-teams/<team>/team.json    团队与任务（agent-teams 的真实状态）
```

## 八、诚实边界

- **阶段推进靠产物，不靠"你跑了哪几个工具"**：所以"结果对不对"取决于产物质量（需求规格是否可判定、方案是否有落点、验收是否有实测），而不是工具调用次数。
- **ponder 还在**（`jarvis_think_deep` / ponder skill / `jarvis_ponder_check`），但它是**可选的深度思考方式**，不是通行证。
- **close 只证明"闸过了 + 没有未完成任务"**，不等于交付质量；质量由三产物闭环 + 覆盖矩阵 + 缺陷记录体现。
- 插件不替模型判断业务对错；它保证的是：**流程顺序、产物位置、职责边界、状态可续**。
