## 〇、需求本质与成功标准

**为谁**：luke-jarvis「数字员工公司操作系统」的维护者/使用者（当前工作区 /opt/work/first）。

**解决什么**：需求模糊时 luke-jarvis 现状 =「问 1-2 个问题 + 代为澄清 + 假设前置」——**引导用户不是现有能力**（t1 实证：skills/jarvis.md:62-64 一次 1-2 问、jarvis.md:64"用户没说清的关键点你代为澄清"、plugin.js:271/1342 分级只看文本长度、agent.cordis.yml:266 ask_user_question 裸调无封装）。用户需求模糊时系统**干等/代答**，不引导；CEO 能力不足时也无"蒸馏行业大佬双人协作"路径。

**怎样算成功（可判定）**：产出一份可执行的需求澄清增强方案，含：
1. CEO 引导流程（专业分析先行→候选问题→三阶提问→判定标准）
2. 蒸馏大佬触发条件（机械可判清单 T1-T5）
3. 双人协作分工（CEO 追验收/大佬追场景，防重复规则）
4. 与现有流程衔接（B16 贾维斯公屏翻译/B22 可行性闸/B15 分层，标注为贾维斯公屏决议）
5. 验收标准（每条机制可判定）
6. **领域无关声明**（通用贾维斯适配所有领域，B51 用户铁律）

## 二、澄清方法基准（t2，判据全部可证伪）

**三阶提问收敛漏斗**（开放式→聚焦式→确认式，每轮 ≤3 问，兼容 jarvis.md"一次只问 1-2 个问题"）：

| 阶 | 目的 | 触发判据 | 满足判据 |
|---|---|---|---|
| 第 1 阶·开放式 | 用户展开（场景/动机/现状） | 原话含模糊词（"大概/差不多/做个系统"）或只给目标没给场景 | 用户说出 ≥1 个具体场景或痛点（含人物/动作/时间） |
| 第 2 阶·聚焦式 | 收敛 1-2 个关键不确定点 | 仍有 ≥2 个候选方向或二义 | 方向收敛到 1 个主目标（最多 2 问） |
| 第 3 阶·确认式 | 复述需求本质确认 | 已收敛，即将进拆解 | 用户明确答复"确认/对"（或修正后再次确认） |

**双人分工基准**：CEO=交付视角（验收/指标/边界/排期承诺），蒸馏大佬=发现视角（场景/动机/细节/专业盲区）。规则：同刻一人主问、问题零重叠、分歧不现场争论、角色不可混、开场引入专家。

**澄清产物基准**：需求本质重述三段式（为谁/解决什么/怎样算成功）+ 假设分级（✅已确认/🔶推断待确认/❓未覆盖）——推断未确认不得当事实用（红线）。

**总判据**：每轮 ≤3 问（数得出）、三阶顺序不跳（动作痕迹）、每问有收敛（"答了什么→收敛了什么"记录）、有需求本质重述（缺一段=未澄清完）、有用户确认记录（无=禁止进拆解）。

## 三、双人协作澄清机制（t3 v3，含多领域示范）

### 3.1 CEO 引导流程（单人模式）

1. **入口判定**：三段式可判定性——为谁/解决什么/怎样算成功齐全且成功标准可判定（有指标/场景/时限）→ 直接进拆解；否则进入引导（未澄清完不得开工）。
2. **CEO 专业分析先行（不干等）**：行业常识 + 同类需求模式（查 .jarvis/cards 与 prototypes）+ 可行域预判（B22 可行性闸预判）→ 产出候选问题清单（把模糊原话翻译成 3-5 个候选问题）。
3. **三阶提问**（采纳 t2）：开放式（"现在怎么做的/哪里最痛/什么场景用"）→ 聚焦式（二选一/必需 vs 可延后）→ 确认式（本质重述复述确认）。
4. **判定标准**：三段式齐全 + 成功标准可判定 + 用户确认记录 + 每问有收敛。

### 3.2 蒸馏触发清单（机械可判）

| # | 触发信号 | 可判定判据 |
|---|---|---|
| T1 | 候选问题生成不足 | 候选问题必须**含具体名词**（对象/场景/行业词）才算数，"再说说/展开讲讲"纯开放追问不计；5 角度中候选为空或仅含无具体名词追问的角度 ≥2 |
| T2 | 同类需求无经验 | .jarvis/cards 与 prototypes 无该领域角色卡/原型（清单可查） |
| T3 | 跨领域知识缺失 | **≥2 个角度引不出行业依据/source**：5 角度中 ≥2 角度候选问题命中行业术语/合规要求，但 CEO 引不出行业规范名/source/案例出处（给得出=不触发） |
| T4 | 用户回答超出专业范围 | 用户回答出现 CEO 无法给出验证动作的断言（查不到对应行业规范/数据源/可核验依据） |
| T5 | 三轮未收敛 | CEO 单人引导 3 轮后仍不可判定（轮数可数） |

**触发后流程**：① 按需求领域现场蒸馏真实大佬（软件→软件大佬、制造→制造大佬，六段式卡过 jarvis_distill 校验，source 必须真实可查——无真实 source 一票否决）；② F5 大佬进场质量验收（第一轮必须贡献 ≥1 个 CEO 问不出的专业问题，无=重蒸馏）；③ 受限环境降级（curl 验证 source：producttalk.org / jipm.or.jp 均 200；或 prototypes 素材蒸馏，标注"受限环境推演"；降级产物验收=大佬卡含 ≥1 条 prototypes 一手素材独有 HOW）；④ 双人进场。

### 3.3 双人协作分工（方案 A：同刻一人主问）

- **谁主问**：同一时刻只有一人主问（另一人记录/思考）；主问者提问后另一人可发补充消息但**必须标注"补充"**。**判据：用户回答前主问者 from ≤1（对话记录可数）；补充消息须带"补充"标注（无标注=违规抢问）**。
- **首问权**：首轮大佬先主问 P1（发现视角开场）、次轮 CEO 主问（交付视角）、交替；首轮 CEO 不补问（记录+观察）；P5 验收留第 3 阶。
- **问题域编号**：P1 场景/P2 现状/P3 痛点/P4 期望/P5 验收，一人只追自己域内（大佬 P1-P4；**CEO 的域 = P5 + 与交付相关的 P2 子集〔频率/负责人/时限〕**）。
- **防重复规则**：重复判定（关键词同域=重复，后问者降级追问具体化）、补充权互不越界（CEO 只补边界/指标/时限，大佬只补例子/例外/频次）、单轮合计 ≤2 问、开场引入专家（透明原则）、分歧不现场争论（记推断假设，会后 jarvis_review 裁决）。
- **收敛协议**：每轮记假设分级；3 轮未可判定→机会树再问 1 轮；仍不可判定→jarvis_review 裁决（不无限盘问）。

### 3.4 双人协作演示 · 软件领域示范之一（"自动写周报"）

**触发**：CEO 对 5 角度 ≥2 个给不出候选问题 → 蒸馏进场。

- 第 1 轮：大佬主问 P1（"在什么场景下觉得非做不可？每周五赶周报花一两个小时，还是领导总说写不到点上？"）；CEO 本轮不补问，记录。
- 用户答："周五下午花 1-2 小时整理很烦，领导嫌不具体。"
- 第 2 轮：CEO 主问 P5 纯交付视角（"做成了怎样算成功——周报自动生成你核对多久能发出？谁验收、全组用还是你一个人用？"）；大佬补充（标注"补充"）："现在周报素材从哪来——提交记录/任务系统/自己回忆？最花时间的是收集还是排版？"
- 第 3 轮：共同输出本质重述：
  - 为谁 = 写周报员工 + 看周报领导；解决什么 = 周五手工收集整理 1-2 小时降下来且内容更具体；怎样算成功 = 自动汇总成草稿、员工核对 ≤5 分钟发出、领导看到具体成果非空话；
  - 假设分级：✅已确认=周五 1-2 小时/领导嫌不具体；🔶推断待确认=素材可来自提交记录/任务系统（须确认）；❓待确认=受众/频率/格式。
- 用户确认重述 = 澄清完成。

### 3.5 多领域示范（B51 通用化铁律：非软件领域完整示范）

> **蒸馏按需求领域现场判断（显式化）**：软件需求蒸馏软件大佬，制造需求蒸馏制造大佬，金融需求蒸馏金融大佬，医疗需求蒸馏医疗大佬——**领域由需求决定，插件无预设**（对齐 README 领域无关设计）。触发机制（T1-T5）与双人分工完全领域无关，仅"蒸馏哪个领域大佬"与"专业盲区问题"随领域变化。

**制造业完整示范：设备检修排期系统**

触发：CEO 对 OEE/TPM/点检标准/法定检定等术语，5 角度中 ≥2 角度引不出行业依据（给不出点检周期标准出处/TPM 规范名/source）→ 触发 T3 → 蒸馏设备维护领域真实大佬（锚点：日本设备维护协会 JIPM，jipm.or.jp 已 curl 200 验证）。

- 第 1 轮：制造大佬主问 P1（"在什么场景下觉得非做不可？是设备突然停机影响生产，还是检修靠经验排、排了又冲突？"）；CEO 本轮不补问。
- 用户答："现在检修靠老师傅经验排，经常和订单排产冲突，停机了才想起来该检修了。"
- 第 2 轮：CEO 主问 P5 纯交付视角（"做成了怎样算成功——停机时间能降多少？谁验收这个系统、单厂用还是多厂共用？"）；制造大佬补充（标注"补充"）："现在检修记录记在哪——纸质点检表还是 Excel？设备按台套还是产线算？有没有强制法定检定（特种设备/安全阀）必须按期做？"
- 第 3 轮：共同输出本质重述：
  - 为谁 = 设备维护工程师 + 生产排产员 + 工厂管理者；解决什么 = 检修排期靠经验且与订单排产冲突、停机才想起检修；怎样算成功 = 系统按规则（上次检修时间/运行小时数/法定检定周期）自动生成检修计划并提前提醒，与排产不冲突，法定检定不漏项；
  - 假设分级：✅已确认=靠老师傅经验排/与排产冲突/停机才想起；🔶推断待确认=检修记录可来自纸质点检表或 Excel；❓待确认=台套或产线/是否含法定检定/提醒提前量。
- 用户确认重述 = 澄清完成。→ 衔接 B16 翻译 → B22 可行性闸 → B15 分层。

## 五、澄清完成标准（可判定）

| 判据 | 判定方式 |
|---|---|
| 需求本质重述三段式齐全 | 为谁/解决什么/怎样算成功，缺一段=未澄清完 |
| 成功标准可判定 | 有指标/场景/时限；"大概、尽量"=未澄清完 |
| 用户明确确认 | 用户对重述答复"确认/对"（或修正后再次确认）；无确认记录=未完成 |
| 假设分级完成 | 推断已显式标注、待确认项已列出；推断未确认当事实用=一票否决 |
| 确认记录入贾维斯公屏 | 经 B16 翻译后的条目已落贾维斯公屏、来源可追溯 |

**五条缺一 = 未澄清完，禁止进拆解。**

## 六、反面问题兜底（质量 F1-F6）

- **F1 用户不配合降级**：判定动作=轮次+回答内容检查（连续 2 轮无响应/1 轮明确拒绝/2 轮无有效信息→不配合）→ 按 CEO+大佬推断完成重述并显式标注"推断待确认"；3 轮无响应=挂起（不进入拆解）。
- **F2 裁决后仍模糊终止路径（降级非默认）**：jarvis_review 裁决"可判定"→ 继续（默认）；裁决"判定不了"且用户明确表示"不知道/你定"→ 才允许带推断+标注开工（用户沉默≠自动降级走 F1 挂起）；终止判据=3 轮+机会树 1 轮+裁决 1 次。
- **F3 防重复统计**：整场两人问题域重复次数 ≤1 为合格，超过=不合格。
- **F4 需求本质版本管理**：重述带版本号+时间戳；用户改口/漂移时旧版本留存，修订记录"v1→v2：用户第 3 轮改口【…】"。

## 七、领域无关声明（B51 用户铁律）

luke-jarvis 是**通用型贾维斯**，必须适配所有领域（金融/制造/医疗/教育/法务/供应链/公共事务等）的人才使用。本方案：
1. **机制层通用化**：入口判定/三阶提问/触发清单/双人分工/完成标准全部**不绑定任何领域术语**（用"场景/现状/痛点/期望/验收"五角度领域无关语言）；
2. **示例多领域化**：制造业完整示范 + 金融/医疗/教育/供应链迷你示例（软件"自动写周报"仅为示范之一，可换任意领域机制不变）；
3. **蒸馏大佬按需求领域现场判断**：软件需求蒸馏软件大佬，制造需求蒸馏制造大佬——领域由需求决定，插件无预设；
4. **与插件既有设计哲学一致**：无静态卡/无领域预设（README.md 领域无关设计）；参照 REFORM-PLAN 办公体系八大支柱的跨领域通用框架风格。
