贾维斯（Jarvis）数字员工公司 · 需求交付全流程

用户从提出需求 → 到验收收口 → 复盘的完整工作链路（领域无关：软件/制造/开店/医院…同一套机制）
角色动作 闸门/校验 产出物 循环 红线/缺陷
0阶段零 · 项目记忆库 & 判领域入口
用户提出需求可能详细、可能模糊（"做个东西"/"你好"）
→
贾维斯查 .jarvis/ 记忆库有无项目沉淀（卡/流程/教训）？有则复用+修订，无则从零
→
判领域方向能判：直接走人才流程
判不出：请用户说具体想干什么（"想做什么/解决什么问题/给谁用"）→ 从描述中判领域
→
领域已定记录需求原文（事实源）+ 项目目录骨架
1阶段一 · 需求打磨（理解透彻才开工）最关键
蒸馏猎头 → 猎头供 CEO猎头=人才调度层（唯一入口）；CEO=该领域公司内部老大（真实大佬，过 distill 双闸）
→
CEO 定领域专家搭档需求最需要的子领域专业视角，猎头调度给 CEO 确认
→
① 独立思考·真疑问才问CEO+专家按角色卡深度思考 → 审视用户信息本身（矛盾/不可行/前提错/更优解）→ 真疑问才用 ask_user_question 问尽（不设数量上限）；思考后无疑问就直接进，不硬凑问题
→
② 蒸馏团队 → 全员各自 ponder每个角色先把需求思考透、有自己的见解（理解需求后才提建议）
→
③ 全体开会畅所欲言（头脑风暴）按角色工作方式风格自由发言；每个提议走"提议→任何人可解答/同意/反驳→全员表态"，辩到多数认同或 CEO 裁决；挑战用户信息本身
→
④ 归拢共识 + 分歧点 + 待用户确认清单 → 写贾维斯公屏；产出"最好的结果"（坏方案淘汰、好方案吸收胜出）
→
澄清完成判定需求本质（为谁/解决什么/怎样算成功）+ 边界 + 优先级 + 约束 + 用户对账确认；缺一继续问
→
《需求规格》产物闸功能清单每条带可判定验收标准 + 参照基准（替代类需求必立）+ 用户确认项 vs CEO 推断项
⚠️ 没规格不进拆解
2-3阶段二·拆解 + 阶段三·领域流程拆解
CEO/架构师拆解把需求拆成功能块/任务（不许随便拆）
→
jarvis_taskgraph 结构闸依赖闭环/无循环/每任务有可判定验收/输入来源明确/编制健康（不许 CEO 一人包办全部）
→
CEO 定领域流程jarvis_process：必经阶段/验收闸门/红线/必须角色/会议触点（按本项目需求特性，不照搬）
→
可行性闸需求超出领域技术边界 → 反馈用户"不可行+依据+替代方向"，不可行项不进任务 DAG
4阶段四 · 建队与派活组建
CEO 写《员工需求单》角色/职责范围/能力经历/思维方式/红线/输出物（详细到猎头能对标真人）
→
猎头逐岗寻访真实权威三重验证（真实存在/方法论独有/对照需求单逐条适配）→ 候选人对标"满足/不满足哪几条+证据"
→
CEO 逐个确认够格不满足 → 通知猎头重找，不拿"将就的人"交差；卡过 distill 双闸 + fidelity 保真度
→
agent_teams 建队name=该领域真实职位名（CEO/厂长/店长…，禁止英文代号）；协同架构设计（jarvis_collab 四要素）
→
CEO 设计任务清单 + 派活任务名/负责人/依赖/验收标准；**派活必带 jarvis_member_brief 开工须知**（含 ponder 执行路径/协议要点/回报格式）；编制硬闸：人配齐才开工
→
《方案设计》产物闸总体方案/接口契约/逐条需求→实现落点/风险对策/验证方式；没方案不许写实现
5阶段五 · 会议驱动协作循环（核心执行期）执行循环
Kickoff 全员会目标/验收标准/领域流程红线/各角色报位置与接口契约
→
各自独思/干活关键决策跑 ponder 满血十阶段（有 run_id 才算真跑）；产出写贾维斯公屏
→
测试角色先出《测试验收单》需求规格每条功能映射测试项+整体验收项（流程/边界/异常）
→
开发-测试迭代循环实现（对照参照基准，禁止自己发挥）→ 独立验证 → 缺陷反馈 → 修复重打包 → 回归 → 直到测试通过
→
黑板即真相 + 按需二次会问题/发现/决策/风险/阻塞集中 jarvis_board；阻塞未决或未决项≥3 → cycle 会；分歧双方 ponder 后 jarvis_review 裁决
→
红线条条问题上行三件套（不许沉默绕行）/ 资源需求上公屏（不许幻觉跳过）/ 卡住不猜着做 / 慢要查根因上报
6阶段六 · 盯控与接管质量保障
CEO 全程盯控agent_teams_status 定期看进度；员工卡住/产出不合格 → 介入
→
jarvis_perf 阶段考核需求对齐度（最重要，做偏=立即换人）/成果质量/完成度/问题上行健康度/角色卡契合度
→
治理分级 L1-L5先纠偏 → 纠偏无效才升级 → 连续2次不达标/需求对齐度=0 → 猎头补位（先交接文档再换人）
→
员工主动猎头补强卡覆盖不了的专业缺口 → 申请现场蒸馏该方向真实大佬作横向支援
7阶段七 · 版本化交付与收口交付
三产物闭环核对需求规格 ↔ 方案设计 ↔ 测试验收单 逐条闭环（jarvis_coverage 自动核查：未覆盖/悬空/未收口/无证据 → 打回）
→
用户视角走查闸以用户身份完整走一遍：主流程连起来+每处细节+弹窗子页+视觉+持续使用段（动态稳定性）；走查有证据（截图/记录）
→
jarvis_release 打版本需求本质逐条 → 交付物 → 自测结果 → 甲方逐条确认（验收单）；可回滚
→
甲方确认？✅ 通过 → 冻结归档
❌ 否决 → 回滚/重做闭环（rollback → 重澄清 → 打新版再交）
⏱ 超时 → 默认通过或明确挂起
→
交付报告 + 收队交付报告面向用户（目标/各岗位产出/风险/交付物在哪怎么验收）；agent_teams_delete 收队（历史保留）
8项目复盘 · 沉淀资产
复盘三问做成了什么 / 哪卡壳了（需求不清/排期/角色不匹配）/ 下次怎么更好——对事不对人
→
沉淀项目记忆库角色卡→cards/、流程→process-*.json、教训→lessons.md、项目细节→project.md（下次需求阶段零直接复用）
→
下次新需求回到阶段零 → 读记忆库 → 复用+修订，不重蹈覆辙
贯穿全流程的红线（违反即缺陷）：① 真实优先，不编造（source/数据/成果一票否决）② 需求本质回归（jarvis_essence 四查：回归本质/防迎合/防幻觉/真实优先）③ 独立思考审视用户信息，不顺着迎合 ④ 头脑风暴产出最好的结果，不走过场 ⑤ 没想透不许做，没验证不许说完成 ⑥ 有问题早暴露（问题上行三件套），不沉默绕行 ⑦ 用户中途/收口后再提需求 = 新需求，同样先打磨再拆解分员工。
