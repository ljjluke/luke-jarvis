## 一、半插件是什么 / 不是什么（能力边界，先读这段）

**已有（装上就能用）**

| 层 | 具体能力 | 位置/证据 |
|---|---|---|
| 工具层 | **29 个 `jarvis_*` 工具** + `/jarvis` 命令（project/store/lesson/process/distill/review/essence/think/think_deep/escalate/capability/collab/perf/meeting/board/release/flowguard/coverage/baseline/taskgraph/fingerprint/member_brief/ponder_check/clarify/company/snapshot/fidelity/update） | `src/host/plugin.js`（ESM）；实测 `TOOLS.length=29` |
| 提示词层 | 每请求注入「jarvis 工作方式 11 步」固定流程，不受上下文压缩影响 | 插件 `systemPrompt` 段（`luke-jarvis:protocol`） |
| 事后闸 | `.jarvis/gates.json` 落闸记录（flowguard）、`.jarvis/docs/ponder-verify/` ponder 核验记录、captain 拦截（成员交活前须有 ponder-verify PASS） | `recordGate` / `checkPonderVerify` / `captainExecutionGuard` |
| 阶段计算 | `computeStage(cwd)` 按**产物+闸门**算出 6 阶段（clarify→decompose→design→build→execute→close），每请求注入「当前阶段/缺口/下一步/事实快照」 | v0.9.0 提交；228 测试含 `computeStage` 用例 |

**没有（这就是「半」的含义，别误解为完全体）**

1. ❌ **没有「工具调用前强制放行」的网关（P2 未做）**：阶段算出来了、缺口也写了，但**它不会机械拒绝**跳步的工具调用。`stage=clarify` 时照样能调 `agent_teams_create_task`——只是提示词和事后闸会劝你/记你。
2. ❌ **没有执行器（P3 未做）**：成员执行仍依赖 captain 回合；captain 回合结束后成员独立存活/完成唤醒**没有**插件级保障。
3. ❌ **不自动推进**：`computeStage` 是只读计算；flowguard 通过后阶段状态靠产物文件变化体现，插件不自己驱动下一步。
4. ❌ 因此：**「跳步被拒」「阶段自动推进」不是本版承诺**（那是 P2/P3 目标，见 `.jarvis/docs/需求规格-luke-jarvis完全体.md` R2/R3/R4）。

> 一句话：**v0.9.0 = 有闸、有阶段计算，但不强制驱动。** 装上能干活，别指望它替你挡跳步。

## 三、安装步骤

### 方式 A：装进 DSH profile（推荐给「使用」场景）

DSH 的包管理入口是 `dsh plugin --profile <name> <pnpm-args...>`（等价于在该 profile 目录执行 pnpm，见 `dsh --help` 用法行）。**顺序=先依赖、后本包**：

```bash
# 1) 先装团队协作依赖（干净环境必须显式装）
dsh plugin --profile web add @nanmicoder/dsh-agent-teams@0.1.20

# 2) 再装本 tgz（绝对路径）
dsh plugin --profile web add /opt/work/first/artifacts/luke-jarvis-0.9.0.tgz

# 3) 确认包进了 profile 依赖（注意：这一步只能证明"装上了"，不能证明"被挂载成 bundle"）
grep -n '"luke-jarvis"' ~/.dsh/profiles/web/package.json
```

**或者用 `file:` 依赖**（开发态，改源码即时生效；本机 web profile 现状即此形态）：

```bash
dsh plugin --profile web add file:/opt/work/first/luke-jarvis
```

⚠️ **三个必须知道的安装事实（实测/读码得出，不是推测）**：

1. **`dsh plugin add` 只写 `dependencies`，不写 `dsh.profile.bundles`**。本机现网 `~/.dsh/profiles/web/package.json` 正是这个状态：`dependencies` 有 `"luke-jarvis"`，`dsh.profile.bundles` 的 8 项里**没有** luke-jarvis。要真正挂载，得在 profile 的 `cordis.patch.yml` 里显式加 `- insert: [{id: jarvis-core, name: luke-jarvis}]`（profile 现有补丁注释已记录：**挂在 preset 的 plugins 里可靠；挂在宿主根层会 `entry not found` 被忽略**——两种写法在现有 profile 注释里都有实测记录，按你的 profile 结构选一种并 `dsh --profile web --dump-config` 验证）。
2. **本包的 `cordis.patch.yml` 会再插入一行 `@nanmicoder/dsh-agent-teams`（`config: {memberMaxDepth: 2}`）**。于是「先 add agent-teams、再 add 本包」会得到**两行同名包**（`id: agent-teams` 与你现有配置行 + 本包的 `id: agent-teams-patch`）。这是本包为了让成员能起一层子 agent（ponder 八卦镜必需）而有意加的，但**它替换 config 而非深合并**：若你现有 agent-teams 配置里 `maxMembers: 32`，新实例只带 `memberMaxDepth: 2`，`maxMembers` 会回落到默认 8。装完请检查 profile 的 patch 里 agent-teams 只有**一行**且 `maxMembers` 符合预期。
3. **两种形态互相覆盖**：profile 里的 `"luke-jarvis"` 只能指向一处。改源码用 `file:`；分发给别人/冻结版本用 tgz。
   ⚠️ 本机 live profile 当前是 `file:/opt/work/first/luke-jarvis`，**本文档的 `dsh plugin add` 命令没有在本机 live profile 上执行**（执行会替换当前活动 profile 的插件解析路径，属破坏性操作）。本机实测的是方式 B（干净 npm 项目）+ tar/测试校验。

### 方式 B：干净 npm 项目里安装（本单已实测，验证「产物本身」）

```bash
mkdir -p /tmp/lj-clean && cd /tmp/lj-clean
npm init -y
npm i /opt/work/first/artifacts/luke-jarvis-0.9.0.tgz    # 实测：added 2 packages（luke-jarvis + agent-teams）
node --test node_modules/luke-jarvis/test/plugin.test.js  # 不带宿主模块 → 见第六节 §1，会 ERR_MODULE_NOT_FOUND
```

这条路径**不挂 DSH**，只验证「包内容完整、可安装、可解开」。它**不是**日常使用方式，也**不是**「装完能跑测试」的证明（原因见第六节 §1）。

### 方式 C：预设 + 技能（想让 `/jarvis` 人设与 ponder 生效，必做，不是可选）

⚠️ **包内 `skills/` 不会自动生效**——DSH 技能发现根只有 `~/.dsh/skills`、`~/.agents/skills`、项目内 `.dsh/skills` 等，**没有** `node_modules/luke-jarvis/skills`。必须手工拷：

```bash

cp -r preset/jarvis-captain.cordis.yml ~/.dsh/.agent-presets/jarvis-captain/            # 严格顶层预设
mkdir -p ~/.dsh/skills/jarvis && cp skills/jarvis.md ~/.dsh/skills/jarvis/SKILL.md
rm -rf ~/.dsh/skills/ponder && mkdir -p ~/.dsh/skills/ponder && cp -r skills/ponder/* ~/.dsh/skills/ponder/
# 自检：ponder 十阶段资源都在
ls ~/.dsh/skills/ponder/stages | wc -l      # 期望 9；少了=没拷全
```

不拷的直接后果：`jarvis_ponder_check` 闸要求 `.jarvis/docs/ponder-verify/` 记录，而成员开工须知把 ponder 路径写死为 `~/.dsh/skills/ponder/scripts/step-guard.cjs` → **干净机上成员第一次交活就被闸卡死**，报错看起来像「ponder 没跑」。

**通过标准**：①`node --check` exit 0 且 `node --test test/plugin.test.js` 输出 `pass 228 / fail 0`；②每类条目至少命中 1 行（`skills/` 应 55 条、`preset/` 应 3 条）；③`npm i` exit 0 且 `node_modules/luke-jarvis/src/host/plugin.js` 存在；④在宿主模块在场的环境里 `pass 228 / fail 0`。

> ⚠️ 反例提醒（都是实测踩到的）：
> 1. **`npm i` exit 0 不能证明产物合格**——安装过程不校验包内文件是否被运行时需要。
> 2. **裸 `node --test` 不是 228**：它会连带跑 `test/e2e-flow.test.mjs`、`test/bagua-gate.test.cjs`，其中 `bagua-gate.test.cjs` 硬编码读 `/tmp/bagua4.json`（仓库里不存在）→ 实测 `tests 230 / pass 229 / fail 1`。**「全绿」必须指明命令**：仓库/文档口径一律 `node --test test/plugin.test.js`（= `npm test`）。
> 3. 裸 `node --test` 在只有 `node_modules` 的目录里可能输出 `pass 0 / fail 0` 且 exit 0（node 22 默认忽略 `node_modules`）——**空绿 = 没跑**。

## 六、已知边界 / 安装版与源码树的差异（诚实清单）

1. **宿主模块未声明（最重要）**：`src/host/plugin.js` 顶层 `import '@deepseek-ai/dsh-tools'`，但 `package.json` 的 dependencies/peerDependencies 都没有它。**后果**：在**不带 DSH 宿主**的独立目录里，插件加载/测试必 `ERR_MODULE_NOT_FOUND`（实测 3/3 失败）；本机仓库树全绿是因为仓库 `node_modules/@deepseek-ai/dsh-tools` 存在（软链到 DSH profile）。**正确用法**：在 DSH profile 内使用/测试；独立目录只验「可安装、可解开」。修不修（补 `peerDependencies`）属于 P2 决策，本单不改源码逻辑。
2. **`office/` 不在包内**：`files` 白名单未列 `office`（24MB 像素办公室静态资源、112 个文件），而插件用 `../../office`（包根 `office/`）托管 `/jarvis-office/*`。**装 tgz 的版本该页面 404**（静默 404，无断言）；源码树（`file:` 依赖）不受影响。要交付该页面：把 `office` 加入 `files` 或单独分发。
3. **`jarvis_update` 读不到自己的版本**：它用 `dirname(import.meta.url)`（=`src/host/`）去找 `package.json` 与 `CHANGELOG.md`，那里都没有 → `localVersion` 兜底 `0.2.0`、变更摘要恒空。**装 v0.9.0 后该工具会显示「本地 0.2.0」**（源码既有行为，本单不改）。另：`v0.9.0-half` 这种非纯 semver tag 也会被它按数字拆分误判（第三段 `Number('0.9.0-half'.split('.')[2])=NaN`）。
4. **`docs/`、`test/`、`scripts/` 整目录进包**：含 `docs/dsh-web-community.diff`、旧流程图 HTML、`docs/archive/` 等与使用无关的文件（体积偏大、功能无损）。`test/` 进包是为了「安装后能自测」（第四节 4 的前提是宿主模块在场）。
5. **`CHANGELOG.md`、`LICENSE` 不进包**：仓库根**没有 LICENSE 文件**而 `package.json` 声明 `BSD-3-Clause`；包内只有 `src/host/vendor/LICENSE-dsh-superagent-MIT.txt` 一份第三方文本。若要对外再分发（market/内网镜像），需补 LICENSE 与 `skills/ponder` 的归属说明，或明确声明仅内部试用。
6. **`skills/` 不自动生效**：见方式 C，必须手工拷到 `~/.dsh/skills/`。
7. **`tag` 与 `tgz` 的相等关系是可判定的「子集」而不是「树相等」**：tag 树 220 个受控文件，tgz 只 99 条（`files` 白名单 + package.json/README）。正确判据=**tgz 内每个文件在 tag 树里逐字节相同**，且 tgz 的 sha256 与清单记录在 artifacts（旁挂文件），而不是要求两边文件数相等。
8. **未在 live profile 实测挂载**：`dsh plugin add` 只写依赖不写 bundles（见方式 A 事实 1）；「装完是否真被挂载」需用 `dsh --profile web --dump-config` 或首次 `/jarvis` 调用确认。

## 七、为什么没有 `npm publish`，以及后续步骤

**原因（真实命令输出）**

- `npm whoami` → `npm error code ENEEDAUTH … This command requires you to be logged in.`（**本机未登录**）；
- `npm view luke-jarvis version` → `E404 Not Found`（**包名未在公共 registry 发布**；registry 本身可达）；
- 因此本单**只交付 tarball + git tag**，**未执行 `npm publish`**（发布到公共 registry 需要账号与包名归属，属用户侧决策）。

**后续步骤（拿到 token 后按序做，别跳）**

```bash
npm login                        # 或 CI 里配 NPM_TOKEN
npm whoami                       # 确认身份
npm view luke-jarvis version     # 404=包名可用；已有版本=需改名或加 scope
npm publish --access public      # 仓库根、版本号正确、git status 干净时执行
git tag -a v0.9.0 -m "npm 发布 v0.9.0"   # registry 版本与 git tag 对齐（当前只有 v0.9.0-half）
```

- 若包名被占用/无权发布 → 改 `name`（如 `@<scope>/luke-jarvis`）后重打包，安装命令同步改；
- 发布后把本文档方式 B 换成 `dsh plugin --profile web add luke-jarvis` / `pnpm add luke-jarvis`；
- ⚠️ 已发出去的 `luke-jarvis-0.9.0.tgz` 若内容与未来 registry 的 0.9.0 不同，**同号不同内容**会让「我装的是哪个」无法从版本号分辨；建议 registry 发布版本 ≥ `0.9.1` 或在 npm 侧用不同版本号，避免覆盖语义。
